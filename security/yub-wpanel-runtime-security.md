# YUB WPanel 运行时安全模型

本文描述当前源码中的主要安全控制、信任边界和已知限制。安全控制用于降低风险，不代表软件、服务器或网站不会被攻破。

## 1. 威胁模型与权限边界

YUB WPanel 负责管理系统服务、网站文件、数据库、防火墙与软件包，因此主服务以 root 运行。完整面板管理员权限应按“可控制整台主机”对待：

- 管理员可创建自定义命令计划任务；未指定普通用户时，该任务通过 `bash -c` 以面板 root 身份运行；
- 多个内部功能会调用系统命令、修改 Nginx/PHP-FPM/systemd/Fail2ban 配置或写入站点文件；
- Commander 白名单保护一部分内部执行路径，但不是覆盖所有功能的沙箱；
- “没有在线代码编辑器或 Web Shell”不等于已认证管理员没有主机级执行能力。

因此，随机入口、双层登录、CSRF 和限速主要缓解未认证攻击以及误操作风险。管理员会话、浏览器或主机一旦失陷，应按整机事件响应：隔离服务器、轮换凭据、检查持久化、从可信备份恢复。

## 2. 登录与会话保护

默认访问需要依次通过：

1. 每台服务器随机生成的入口路径；
2. HTTP BasicAuth；
3. Web 管理员登录与会话。

随机路径只能降低批量扫描噪声，不能替代认证。BasicAuth 与 Web 登录失败会进入限速/封禁流程；实际效果仍取决于正确的代理/IP 配置和 Fail2ban/nftables 状态。

面板登录密码使用 bcrypt cost 12 保存。bcrypt 能提高离线猜测成本，但弱密码仍可能被字典攻击。浏览器登录时明文密码必须交给本机面板验证，传输安全依赖 TLS 及客户端对证书身份的正确验证。

Session Cookie 使用 `HttpOnly`、`Secure` 与 `SameSite` 属性。受浏览器 CSRF middleware 保护的写路由要求 CSRF token；内部 API、迁移协议或其它认证方式可能采用不同保护，不能概括为“所有写操作都使用同一种 CSRF 机制”。XSS 即使不能直接读取 HttpOnly Cookie，也可能在受害者浏览器中发起已认证操作，因此模板转义、CSP 和输入校验仍然重要。

## 3. TLS 的作用与限制

面板通常在 8443 上直接提供 HTTPS。TLS 可以保护传输机密性和完整性，但前提是客户端正确验证证书与目标服务器身份。

fresh install 的初始证书为自签名证书。首次连接前应通过 SSH 核对 SHA-256 指纹，长期公网使用应换成可信证书并限制管理端口来源。无条件忽略浏览器证书警告会削弱对中间人攻击的防护。

HTTP 安全头、请求头读取超时、空闲连接超时和最大请求头大小用于降低常见浏览器及慢连接风险。长时间或大文件业务需要单独测试，不能只依赖这些默认值。

## 4. 凭据与敏感数据

- 面板登录密码以 bcrypt 哈希保存；
- MariaDB root 密码、远程备份、SMTP、Webhook、AI 或迁移等功能所需凭据可能以可恢复形式保存在 root-only 配置或面板数据库中；
- `config.json`、`panel.db`、站点身份文件、证书私钥和备份都应按敏感资产保护；
- 文件权限是重要控制，但不能抵抗已经取得 root 的攻击者；
- 备份必须加密、限制访问并定期做恢复演练。

向支持人员提供日志或数据库前，应先脱敏 URL、域名、IP、用户名、令牌、密钥和连接信息。

## 5. 面板更新供应链

当前面板更新顺序为：

1. 从 GitHub Release 或管理员配置的 HTTPS 反代获取二进制、SHA-256 清单与签名；
2. 用内置 Ed25519 公钥验证清单签名；
3. 严格解析清单并核对二进制 SHA-256；
4. 运行已验签候选程序的 `--info` 兼容性预检；
5. 备份当前二进制和面板 SQLite；
6. 原子替换并启动；
7. 由 watchdog 在限定时间内检查健康状态。

签名把资产哈希绑定到发布密钥；SHA-256 检测资产与已签名清单是否一致；预检只是一项兼容性烟测，不是第三种密码学证明，而且会执行已验签的候选程序。更新器对 GitHub Release 元数据、面板二进制、SHA-256 清单和 Ed25519 签名分别设置 1 MiB、256 MiB、4 KiB 和 64 bytes 的硬上限；既预先拒绝已知超限的 `Content-Length`，也通过受限读取拒绝无长度或分块传输的实际超限响应，并清理未完成文件。

健康检查失败时 watchdog 会尝试恢复旧二进制，并在检测到面板数据库结构不可读时尝试恢复数据库。以下限制必须保留在风险判断中：

- 回滚本身可能失败；
- 合法但已经升级的数据库不一定回退；
- 面板目录外的 Nginx、PHP、Fail2ban、WordPress 插件、站点文件或站点数据库副作用不在完整回滚保证内；
- watchdog 作为 transient systemd unit 只保护当前更新事务；主机或 systemd 在握手/健康窗口中重启时，不保证该临时单元会在开机后继续执行，必须通过带外通道检查服务、回滚计划和备份；
- 面板内在线更新只替换并验证二进制，不会刷新安装时写入 `/usr/share/doc/yub-wpanel` 的许可归档；需要同步许可材料时，应使用同一固定 Release 的已验签安装器执行 repair；
- 自动更新默认关闭；管理员启用后，调度器可在维护窗口自动下载并安装。

更新前仍需读取 Release Notes，创建主机/业务备份，并确认有带外恢复通道。

### 发布工作流边界

Release 工作流把构建、签名和发布分成独立 job：普通构建不接收签名私钥；签名 job 不 checkout 或执行仓库程序；只有发布 job 获得仓库内容写权限。官方 Actions 固定到审核过的完整 commit SHA，前端静态资产来自当前提交而不是构建时 CDN。

签名 job 从 GitHub Actions Secret 读取私钥。仓库源码无法证明账户权限、审批策略或离线备份实际如何管理；这些必须由仓库管理员另外配置和审计。签名覆盖明确列出的二进制与安装器资产，不覆盖 GitHub 自动源码包，也不是可复现构建或漏洞不存在的证明。

## 6. 系统命令与文件操作

内部执行层对部分命令、参数和 URL 做白名单/格式校验，并对许多配置采用临时文件、语法检查与原子替换。这些措施可以降低命令注入和部分写入风险，但适用范围必须逐功能确认。

需要特别注意：

- 自定义命令计划任务是明确的高权限功能，可使用 `bash -c`；只向完全可信的管理员开放；
- 远程文件导入允许经过 SSRF/地址检查的公网 HTTPS 来源，并非只允许一个固定域名；
- AI、Webhook、SMTP、S3、SSH、站点迁移和商业插件下载会使用管理员提供的目的地或凭据；
- 静态 Go 二进制只是分发形式，不能防止输入处理、内存安全以外的逻辑漏洞或命令注入；
- 任何路径、符号链接、权限、owner 或原子替换检查都有实现边界，需要持续测试。

不使用自定义命令时应删除相关任务；必须使用时优先指定权限受限的系统用户，不要把来自请求、域名、文件名或远端响应的未验证内容拼入命令。

## 7. 网站与 WordPress 保护

YUB WPanel 为站点配置独立系统用户、PHP-FPM pool 和数据库，减少常见站点之间的直接影响。维护窗口、文件锁、更新前备份、升级后健康检查与失败恢复用于降低管理操作风险。

这些控制不构成绝对隔离：共享内核、root 面板进程、Nginx、MariaDB、Redis、系统包和管理员凭据仍是共同依赖。WordPress 核心、主题和插件更新可能引入回归或新漏洞；及时更新通常降低已知漏洞风险，但不保证不会被入侵。

文件锁、维护模式、密码恢复策略和配套插件都可能因权限、异常配置或站点自定义而失败。重要站点应在更新后人工检查前台、后台、登录、表单、订单、缓存和定时任务。

## 8. 防火墙、扫描与告警

面板会配置或调用 Fail2ban、nftables/UFW，并分析面板及站点日志以识别登录爆破、常见敏感路径扫描、SQL 注入特征和伪装搜索引擎等行为。

日志规则与自动封禁只能缓解已覆盖的模式，可能漏报或误报。可信代理/CDN 的真实客户端 IP 配置错误会影响限速和封禁对象。启用前应确认 SSH/带外访问可用，启用后定期检查 jail、nftables 规则和误封恢复流程。

AI 诊断与异常分析提供证据和建议，不应被当作自动取证结论。高风险事件仍需核对原始日志、进程、文件哈希、账号与网络连接。

## 9. 出站网络边界

正常运行不只连接 GitHub。实际目标按功能分为：

| 类型 | 典型目的地 | 触发条件 |
|---|---|---|
| 默认后台 | GitHub API/raw、WordPress API/wordpress.org | 面板版本/公告、WordPress 备用包或版本检查 |
| 管理员操作 | GitHub Release/反代、WordPress 下载、Let’s Encrypt、公开 HTTPS 远程导入、站点迁移目标 | 点击更新、签发证书、导入或迁移等 |
| 安全数据 | Cloudflare、Google、Bing 公布的 IP 列表 | 搜索引擎/代理地址刷新或安全分析 |
| 管理员配置 | SMTP、Webhook、AI API、S3、SSH、GitHub 反代、自定义遥测端点 | 对应功能启用后 |

网络目标与频率应在出口防火墙、代理或 DNS 日志中审计。管理员提供的代理或第三方端点成为新的信任边界。

### 遥测

运行时遥测默认关闭，默认端点为空。只有配置自定义端点并启用后，程序才会发送；首次明确启用会唤醒后台调度，无需重启面板，之后按日调度：

```json
{
  "anonymous_id": "machine-id 的 SHA-256 截断值",
  "version": "面板版本"
}
```

这个 ID 在同一主机上稳定，应称为伪匿名而不是不可关联匿名值。JSON 不包含业务内容或 IP 字段，但 HTTP 接收端通常能看到源 IP、时间与传输元数据。保存端点时与实际连接时都会拒绝回环、私网、链路本地和保留地址；遥测客户端不跟随 HTTP 重定向，降低 DNS 变化或重定向触达内网的风险。关闭后应复查数据库设置与出口日志确认没有上报。

## 10. 系统包与漏洞管理

Nginx、PHP、MariaDB、Redis、Fail2ban 等主要服务器组件通过 APT 获取，面板二进制和 WordPress/WP-CLI 使用各自分发渠道。来源签名用于认证发布者和完整性，不证明软件没有安全缺陷。

建议：

- 订阅 Debian、PHP、WordPress 与 YUB WPanel 安全公告；
- 在应用系统或面板更新前保存可恢复备份；
- 先在同版本测试机验证关键业务；
- 定期运行 `apt update`、检查可升级包和服务重启需求；
- 删除不需要的插件、主题、计划任务、外部集成和管理员账号。

## 11. 运行检查清单

```bash
# 服务与近期日志
systemctl status yub-wpanel --no-pager
journalctl -u yub-wpanel -n 100 --no-pager

# 管理端口与证书指纹
ss -lntp | grep ':8443'
openssl x509 -in /www/server/panel/certs/panel.crt -noout -fingerprint -sha256

# 配置权限（不要把内容直接发给第三方）
stat /www/server/panel/config.json /www/server/panel/panel.db

# 防火墙和 Fail2ban
nft list ruleset
fail2ban-client status
```

此外应定期验证：备份可恢复、管理员账号最小化、自定义命令任务确有必要、外部凭据已轮换、出口连接符合预期、网站与面板补丁处于支持版本。

## 12. 安全事件处理

怀疑面板或主机被入侵时：

1. 使用云厂商控制台或带外通道隔离公网访问；
2. 不要先删除日志或盲目重装；保存磁盘/主机快照与时间线；
3. 从独立可信设备轮换云账号、SSH、面板、数据库、备份、API 和站点管理员凭据；
4. 检查 systemd、cron、用户、SSH key、Nginx/PHP、Fail2ban、站点文件、WordPress 管理员与插件；
5. 从已知可信备份恢复到新主机，并在恢复前修复进入路径；
6. 通过 GitHub Security 提交最小化、已脱敏的复现与证据。

纵深防御的价值在于让攻击更难、让异常更容易发现、让恢复更可控，而不是提供“绝不会失陷”的保证。
